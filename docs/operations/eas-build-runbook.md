# EAS build runbook

Operational reference for producing iOS + Android builds via EAS Build
against the **`million-labs`** Expo org. Originally drafted against
Expo SDK 55 at the time of S0 init (2026-06-23); flipped to
**Expo SDK 54** later that same day per the SDK downgrade plan at
`.mstack/plans/2026-06-23-expo-sdk-54-downgrade.md`. EAS CLI ≥ 12.0
either way.

> - [.mstack/reviews/2026-06-22-eas-project-init.md](../../.mstack/reviews/2026-06-22-eas-project-init.md)

## Prerequisites

- An EAS account with at least Developer access to the `million-labs`
  Expo org. (Owner-level access is required for the very first
  `eas init` — the project's create-permissions check.)
- Apple Developer account with the AIRA app's bundle ID
  `com.airabynisarga.app` registered + tied to a team.
- Google Play Console access with the AIRA app's package
  `com.airabynisarga.app` available.

### EAS CLI

Two install options depending on cadence:

```bash
# One-shot use (Replit shell, occasional builds):
pnpm dlx eas-cli@latest <command>

# Persistent install (you live in EAS):
npm install -g eas-cli
```

`pnpm dlx` is the recommended path for the Replit shell — it avoids
polluting the global npm prefix that Replit doesn't always clean
between sessions.

### Authentication

Two paths; try the first, fall back to the second if the Replit
terminal flow is broken:

1. **Interactive login:**
   ```bash
   pnpm dlx eas-cli@latest login
   ```
   Opens a device-auth flow in the terminal; paste a code at the URL
   the CLI prints.

2. **Personal access token** (fallback, or for CI):
   - Visit https://expo.dev/settings/access-tokens
   - Create a token scoped to the `million-labs` org.
   - In the Replit shell:
     ```bash
     export EXPO_TOKEN=<paste-token>
     ```
   - Confirm: `eas whoami` should show your account.

## One-time setup (already done)

These tasks are documented here for reference — they were executed once
during the S0 init.

- `eas init` ran from `apps/mobile/` and bound the project to
  `million-labs`. Wrote `extra.eas.projectId` into
  `apps/mobile/app.config.ts`.
- `eas update:configure` wrote `updates.url` (the
  `https://u.expo.dev/<projectId>` endpoint) and
  `updates.fallbackToCacheTimeout` into `app.config.ts`.
- `eas.json` has three build profiles: `dev` (simulator + dev-client),
  `preview` (internal distribution, EAS Update channel `preview`), and
  `production` (store distribution, EAS Update channel `production`,
  `autoIncrement: "buildNumber"`).
- Apple credentials uploaded via `eas credentials --platform ios`:
  App Store Connect API key + Apple Push Key (`.p8`) for APNs.
- Android upload keystore generated by EAS on the first Android build;
  backed up to 1Password per
  [eas-keystore-backup.md](./eas-keystore-backup.md).

## First-build prompts (one-time)

The very first build per platform will prompt for the initial build
counter because `eas.json` has `appVersionSource: "remote"` — EAS
holds the canonical buildNumber/versionCode. **Accept the default
value `1`** when prompted. EAS auto-increments from there via the
`production` profile's `autoIncrement: "buildNumber"`.

## Building

All `eas build` commands run from `apps/mobile/`:

```bash
cd apps/mobile
```

### Simulator iOS build (free, no credentials)

```bash
pnpm dlx eas-cli@latest build --platform ios --profile dev
```

- No Apple credentials required.
- Output: a runnable iOS Simulator app you can drag into Simulator.
- Use this to validate the EAS-Build wiring end-to-end before
  spending credentials on signed builds.

### Preview build (internal distribution)

```bash
# Both platforms in parallel:
pnpm dlx eas-cli@latest build --platform all --profile preview

# Or one platform at a time:
pnpm dlx eas-cli@latest build --platform ios --profile preview
pnpm dlx eas-cli@latest build --platform android --profile preview
```

- iOS: signed IPA with internal-distribution provisioning. Install
  via TestFlight invite OR sideload via Apple Configurator on a UDID
  registered to the team.
- Android: APK suitable for sideloading. Email/airdrop the file to
  testers; they install via "Unknown sources" on their device.
- Channel: `preview` — EAS Update OTAs published with
  `eas update --branch preview` flow to this build.

### Production build (store-ready)

```bash
pnpm dlx eas-cli@latest build --platform all --profile production
```

- iOS: signed IPA with distribution provisioning, ready for
  TestFlight + App Store submission.
- Android: signed AAB (Android App Bundle), ready for Play Console
  upload.
- Channel: `production` — EAS Update OTAs published with
  `eas update --branch production` flow to this build.

### Watching the build

The CLI prints a dashboard URL like:
```
🤖 https://expo.dev/accounts/million-labs/projects/aira-mobile/builds/<uuid>
```

Builds take 10–25 minutes depending on platform + queue. Once complete:
- Download artifact from the dashboard.
- iOS: install on Simulator (dev) or invite via TestFlight (preview /
  production).
- Android: install APK directly (preview) or upload AAB to Play
  Console (production).

## OTA hotfix flow (EAS Update)

Once a build is in users' hands, JS-only changes can ship without a
new native build:

```bash
# From repo root or apps/mobile — either works:
pnpm dlx eas-cli@latest update --branch production --message "Fix typo in /home"
```

This bundles the current JS state of `apps/mobile/` and publishes it
to the `production` branch (which by default maps to the `production`
channel). Builds installed from a profile that uses
`channel: "production"` check this branch and apply the update on next
app cold-start.

> **Channel-to-branch mapping** defaults to **channel == branch**.
> Don't change this in the Expo dashboard without coordinating —
> mis-mapped publishes silently miss the cohort they intend to
> reach.

### `runtimeVersion` ceremony

`app.config.ts` has `runtimeVersion: { policy: "appVersion" }`. OTAs
flow only within a marketing version:

- `version: "0.1.0"` → OTAs reach 0.1.0 clients.
- Bumping to `version: "0.2.0"` → 0.1.0 clients **stop** receiving
  OTAs; next OTA reaches only 0.2.0 clients (and only after they
  install a fresh 0.2.0 native build via store).

Sequence at S7 store launch:

1. Bump `version: "0.1.0"` → `"1.0.0"` in `app.config.ts`.
2. Run new `production` builds for both platforms.
3. Submit to App Store + Play Store.
4. Once review approves + the build is live: future OTAs ship to
   `1.0.0` clients via `eas update --branch production`.
5. 0.1.0 clients (TestFlight legacy) stop receiving updates —
   acceptable because they'll have moved to 1.0.0 by then.

## Common failure modes

### "Failed to fetch provisioning profiles"

App Store Connect API key has insufficient access scope. EAS needs
**Admin** or **App Manager** access. "Developer" is insufficient.

Fix: regenerate the API key at the right access level via Apple
Developer portal → Users and Access → Integrations → App Store
Connect API. Upload the new key with:

```bash
pnpm dlx eas-cli@latest credentials --platform ios
```

### "Push key creation denied: limit reached"

Apple caps each team to **2 active APNs Auth Keys**. If you already
have 2, you can't create a third. Either:

- **Reuse** an existing key — during `eas credentials --platform ios`,
  pick the "Use an existing key" option and supply the `.p8` file.
- **Revoke** a stale key from Apple Developer portal → Keys, then
  create a new one.

### `eas init` finishes with "Cannot automatically write to dynamic config"

Misleading error message — the project IS created on Expo's side. The
exit code is non-zero but the URL it printed (`expo.dev/accounts/.../projects/<slug>`)
resolves to a real project record. EAS just can't auto-write to
`app.config.ts` because it's a function (dynamic) form, not static
JSON.

Fix: copy the suggested `extra.eas.projectId` block from the CLI output
and paste it into `app.config.ts` manually. Format:

```ts
extra: {
  eas: {
    projectId: "<uuid>",
  },
},
```

Subsequent `eas` commands read this value and work normally.

### `eas init` writes to `app.json` instead of `app.config.ts`

There's a stray `app.json` confusing the CLI. We use `app.config.ts`
exclusively.

Fix:
```bash
ls apps/mobile/app.json  # should NOT exist
# If it does, delete it and re-run `eas init`:
rm apps/mobile/app.json
pnpm dlx eas-cli@latest init
```

### Interactive `eas login` hangs in Replit shell

The device-auth flow needs an interactive terminal. Replit's web shell
sometimes loses the input stream.

Fallback: use `EXPO_TOKEN` env var (see Authentication above).

### Build fails with "EACCES: permission denied, rmdir" during tarball upload

Replit-specific cache contention. EAS CLI compresses the project to a
tarball under `/tmp/runner/eas-cli-nodejs/<uuid>-shallow-clone/` and
during cleanup tries to `rmdir` a `.cache/dotslash/.../React Native
DevTools-linux-x64` subdir. Replit's `/tmp/runner` permissions block
the rmdir, the cleanup fails, and the build aborts before reaching
EAS Build compute. **No billing impact** — the upload never
finished.

EAS-side state (channels, branches, generated keystores, uploaded
credentials) persists across the failed attempt. You don't need to
redo anything; just retry the build command after clearing the
cache.

Fix:
```bash
# Wipe the stuck cache:
rm -rf /tmp/runner/eas-cli-nodejs 2>/dev/null
# If rm fails with permission denied:
chmod -R u+w /tmp/runner/eas-cli-nodejs 2>/dev/null
rm -rf /tmp/runner/eas-cli-nodejs

# Also defensive (rarely needed):
rm -rf ~/.eas-cli 2>/dev/null
rm -rf /tmp/eas-build-*  2>/dev/null

# Then re-run:
cd apps/mobile
pnpm dlx eas-cli@latest build --platform all --profile preview
```

### Build fails with "package.json: expo-updates not found"

The `expo-updates` package was added in T3 — confirm `pnpm install`
ran cleanly after the dependency was added. From repo root:

```bash
pnpm install
```

### `eas init` rejects eas.json: "autoIncrement must be a boolean"

EAS Build's schema for `autoIncrement` at the profile top level is a
**boolean** (`true`/`false`), not a string. The `"buildNumber"` and
`"versionCode"` string forms are only valid one level deeper:

```jsonc
// WRONG — fails at eas init:
"production": {
  "autoIncrement": "buildNumber"
}

// RIGHT — increments both platforms automatically:
"production": {
  "autoIncrement": true
}

// ALSO RIGHT — per-platform string form:
"production": {
  "ios":     { "autoIncrement": "buildNumber" },
  "android": { "autoIncrement": "versionCode" }
}
```

We picked the simple `true` form because `appVersionSource: "remote"`
gives EAS full control over both counters anyway.

### Build fails with "missing native config"

EAS Build creates the native iOS/Android project on-the-fly from
`app.config.ts`. If your tree has a stray `apps/mobile/ios/` or
`apps/mobile/android/` folder from a local `expo prebuild` run, EAS
uses those instead and may fail. We don't commit native folders —
they're gitignored. If they exist locally, delete them:

```bash
rm -rf apps/mobile/ios apps/mobile/android
```

## SDK pin policy

AIRA's mobile is pinned to the SDK that the publicly-shipped Expo Go
client bundles (currently **SDK 54**) so the scan-the-QR iteration
loop works without sideloading a custom Dev Client. Background
reasoning lives in the feedback memory
`.claude/projects/-home-runner-workspace/memory/feedback_expo_sdk_for_iteration.md`.

Rules:

- **Never hand-pick a peer version.** Every `expo-*` / `react-native*`
  / `react` / `react-dom` / `@expo/*` peer is resolved by
  `npx expo install --fix` against the active `expo` major. Picking
  one yourself is how F21 T12 ended up on the pre-version-alignment
  `expo-notifications` line by mistake (see the 2026-06-23 decision
  log).
- **To upgrade**: edit `apps/mobile/package.json` to set the new
  `expo` major (e.g. `~56.0.0`), run `pnpm install --filter
  @aira/mobile`, run `pnpm --filter @aira/mobile exec expo install
  --fix`, then `pnpm install` to sync the workspace lockfile. The
  resolver does the rest.
- **To downgrade**: same flow in reverse. Re-evaluate the
  `pnpm.overrides` block at the workspace root (`@types/react` +
  `@types/react-dom`) — the SDK-aligned React types version probably
  changed.
- **Marketing `version` bumps** are independent of SDK changes.
  Only bump `version` (in `app.config.ts`) when you want to fork
  the OTA cohort (real-device users on the old build won't pull
  the new bundle).

## When to ask Expo support

- Org-level billing or quota issues.
- Build queue stalled > 1 hour with no error.
- Credentials wiped from EAS for an unknown reason (we have the local
  keystore backup, so this isn't catastrophic — but worth filing).
- Push key revoked outside of `eas credentials` (Apple-side action).

Otherwise the runbook should cover the 90% case. Surfaced issues
should be added back here.
