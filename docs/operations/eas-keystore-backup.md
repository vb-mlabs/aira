# Android upload-keystore backup

The Android upload keystore generated by EAS on the first Android build
is **the app's identity**. If you ever lose it AND lose access to the
Expo project, you cannot ship a new version of AIRA to Play Store
under the same listing — you'd have to publish a new app with a
different package and migrate users manually. There is no Apple-style
"revoke and reissue" path.

This one-shot procedure downloads the keystore to a secure store the
moment it exists, so EAS's copy is no longer the single point of
failure.

## When to run this

**Immediately after the first Android EAS build completes.** That's
when the keystore first exists; before then there's nothing to back
up.

In the implementation plan this is **Task 8** of the S0 init flow.

## Procedure

From `apps/mobile/`:

```bash
pnpm dlx eas-cli@latest credentials --platform android
```

The CLI presents a menu. Walk it:

1. Pick the project (defaults to AIRA — confirm).
2. Pick the build profile to configure credentials for — pick
   **`production`** (the keystore is shared across profiles for the
   same app, but the production profile is the canonical one).
3. From the credentials menu, pick **"Keystore: Manage everything
   needed to build your project"**.
4. From the keystore submenu, pick **"Download credentials from Expo
   to local JSON"**.
5. The CLI writes a JSON file to your local filesystem. **Path is
   printed at the end** — note it carefully. Default location is
   `apps/mobile/credentials.json` or similar.

The downloaded file contains:
- A base64-encoded `.jks` keystore blob.
- The keystore password.
- The key alias.
- The key password.

> **NEVER commit this file to git.** It is `.gitignore`d at the repo
> root via the catch-all `credentials.json` rule. Run `git status` after
> the download to confirm it's not staged.

## Where to store the backup

**Primary:** 1Password vault entry titled **"AIRA Android Upload Keystore"**.

- Use 1Password's "Secure Note" type or "Document" type.
- Attach the entire downloaded JSON as a file attachment.
- In the notes field, capture:
  - Date downloaded (e.g. `2026-06-22`)
  - Replit shell where it was generated
  - The keystore's SHA-256 fingerprint (visible via the EAS dashboard
    or via `eas credentials` "View credentials" submenu) — this is
    the SAME value that goes into `assetlinks.json`, so having it
    in 1Password also speeds up future fingerprint lookups
- Restrict the vault to the small set of people who need it (you,
  and a designated backup admin — not the full team).

**Secondary (recommended):** offline hardware key or encrypted disk
stored in a different physical location.

- USB drive encrypted with a passphrase NOT stored in 1Password.
- Or a YubiKey-encrypted file.
- The goal: if 1Password is compromised AND the Expo project is
  compromised, you still have the keystore.

**DO NOT** store the keystore:
- In email.
- In any cloud doc service that doesn't require explicit decrypt
  (Google Drive, Dropbox, etc.) — even private folders.
- In any chat tool (Slack, Discord, Telegram).
- In the repo, even encrypted.

## Verify the backup is restorable

Before deleting the local download or relying on the 1Password copy
alone, confirm you can put it back:

```bash
# In a scratch directory:
cd /tmp
mkdir restore-test
cd restore-test

# Copy from 1Password attachment, name it credentials.json:
# (your-1password-flow-here)

# Verify it parses + has the expected shape:
node -e "
const c = require('./credentials.json');
console.log('has android key:', !!c.android);
console.log('has keystore:', !!(c.android && c.android.keystore));
console.log('keystoreFormat:', c.android && c.android.keystore && c.android.keystore.keystoreFormat);
"

# Expected output:
# has android key: true
# has keystore: true
# keystoreFormat: jks
```

If those checks pass, the 1Password copy is restorable. You can now
safely delete the local download:

```bash
shred -u credentials.json  # or: rm credentials.json
```

## If you ever need to restore

If the EAS project is wiped or you migrate to a new account:

```bash
# In apps/mobile/:
pnpm dlx eas-cli@latest credentials --platform android
```

Pick "Keystore: Manage everything needed to build your project" →
"Upload existing credentials". Point at the restored
`credentials.json`. EAS pulls the keystore into the project and
future builds sign with the same identity.

The next build will produce an AAB with the same SHA-256 fingerprint
as previous releases — Play Store accepts the upload + ships the
update to existing users.

## What goes wrong if you don't do this

You don't lose the app — you lose the **identity of the app**.

- Play Store identifies an app by the signing key's SHA-256
  fingerprint, NOT by the package name.
- If you can't sign with the same fingerprint, Play Store treats your
  new builds as a different app. Your existing users do not get
  updates. They have to find your new listing, install fresh, lose
  any local data.
- There's no Play-side reset — Google doesn't let you re-key an
  existing app under any circumstance.

This is the only situation in the entire MVP where a single missing
backup makes the app unshippable. Take the 15 minutes.
