## Summary

Plan is ready to implement with two corrections: (1) `apps/web/src/app/api/v1/waitlist/route.ts` was missing from files-to-touch — the existing `onConflictDoNothing({ target: waitlist.email })` call breaks when the single-column unique constraint is replaced with the composite `(email, type)` unique, and must be updated in the same task as the DB schema change; (2) the frontend form should use `apiClient.post()` (CLAUDE.md convention for Client Components), not raw `fetch`. All open questions from the plan are now resolved.

## Findings

### Blockers (resolved before approval)

- **Existing `/api/v1/waitlist` route breaks after migration.** The call `.onConflictDoNothing({ target: waitlist.email })` references the single-column `UNIQUE(email)` constraint which the migration drops. The route must be updated to `.onConflictDoNothing({ target: [waitlist.email, waitlist.type] })` in the same commit as the DB schema change. Added to Task 1.

### Concerns (raised, decided, recorded)

- **Concern:** Plan said "existing route unchanged" — actually needs updating.
  **Decision:** Fixed — route update folded into Task 1 (same atomic commit as schema + migration).

- **Concern:** Frontend form fetch pattern — `useState` + raw `fetch` vs `apiClient.post()`.
  **Decision:** Use `apiClient.post()` from `@/lib/api-client` per CLAUDE.md Client Component convention.

- **Concern:** `validators/src/index.ts` edit listed in plan.
  **Decision:** No edit needed — index uses `export * from "./waitlist"` which auto-exports new symbols. Removed from files list.

- **Concern:** `GOOGLE_FORM_URL` constant and `TODO` comment become dead code.
  **Decision:** Remove both as part of Task 5 (frontend form).

### Suggestions (taken)

- Email template copy uses contact-expectation tone: "We'll reach out via your preferred channel soon." Sets the right expectation given the form explicitly collects contact preference.

## Decisions locked

1. Existing `/api/v1/waitlist` route updated in Task 1 (same commit as schema).
2. Frontend form uses `apiClient.post()`.
3. Business welcome email: contact-expectation tone.
4. Phone validation: permissive (any non-empty string).
5. Source value for business form: `'business-listing-cta'`.
6. `validators/src/index.ts` requires no edit (barrel auto-re-exports).

## Implementation plan

### Task 1: DB schema + migration + fix existing waitlist route

- **Files:**
  - `packages/db/src/schema/waitlist.ts` (edit)
  - `packages/db/src/migrations/` (new — generated by `pnpm db:generate`)
  - `apps/web/src/app/api/v1/waitlist/route.ts` (edit)
- **What:**
  1. In `waitlist.ts`: remove `.unique()` from the `email` column. Add columns: `type text NOT NULL DEFAULT 'consumer'`, `full_name text`, `business_name text`, `phone text`, `preferred_contact text`, `preferred_time text`. Add to the table callback: `uniqueIndex('waitlist_email_type_unique').on(table.email, table.type)`, `check('waitlist_type_check', sql\`${table.type} IN ('consumer','business')\`)`, `check('waitlist_preferred_contact_check', sql\`${table.preferred_contact} IS NULL OR ${table.preferred_contact} IN ('phone','whatsapp','email')\`)`, `check('waitlist_preferred_time_check', sql\`${table.preferred_time} IS NULL OR ${table.preferred_time} IN ('morning','afternoon','evening','anytime')\`)`. Also add `'business-listing-cta'` to the existing `waitlist_source_check` enum list.
  2. Run `pnpm db:generate` to produce the migration SQL file. Do not run `pnpm db:migrate`.
  3. In the existing `/api/v1/waitlist/route.ts`: change `.onConflictDoNothing({ target: waitlist.email })` → `.onConflictDoNothing({ target: [waitlist.email, waitlist.type] })`.
- **Acceptance:**
  - `pnpm typecheck` passes
  - A new file exists under `packages/db/src/migrations/` with SQL that drops `waitlist_email_unique`, adds the composite unique, and adds the new columns and checks
  - The existing waitlist route compiles without errors
- **Pause if:** The generated migration SQL drops any column or includes a data-destructive `ALTER TYPE` — escalate before proceeding.
