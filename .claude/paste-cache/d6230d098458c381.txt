  In this repo, we hit the same class of error — fs.rmSync fails with EACCES on Expo Go's React Native DevTools binary in
  .cache/dotslash/.../ because it's dropped with restrictive permissions. The fix is don't fight it, log and continue:

  try {
    fs.rmSync(abs, { recursive: true, force: true })     
    console.log(`[deploy-prune] removed ${rel}`)
    return true
  } catch (err) {
    console.warn(`[deploy-prune] skip ${rel} (${err.code ?? err.message})`)
    return false
  }

  Key reasoning (lines 32-37):
  - Pruning is best-effort. A failed delete = slightly larger image, not a broken deploy.
  - The offending file is React Native DevTools-linux-x64 from .cache/dotslash/... with restrictive perms.
  - Aborting the whole deploy over one undeletable file is worse than leaving it.

  How to apply to your other app — pick the right one based on root cause:

  1. If it's a deploy/cleanup script (best-effort pruning): wrap fs.rmSync / rimraf in try/catch and log+continue. Same pattern as above.
  2. If it's runtime code that must succeed: the EACCES is usually because:
    - The file/dir is owned by another UID (root vs runtime user — common in containers)
    - The parent dir lacks write permission (rmdir needs write on the parent, not on the dir itself)
    - The dir is non-empty and you're using rmdir instead of rm -rf / fs.rmSync({recursive:true})
    - A bind mount or read-only volume
  3. If it's a .cache / DevTools file specifically (sounds like your case if it's also Expo/RN): add the offending path to .dockerignore
  / .easignore / your deploy-prune skip list so it never gets created in the runtime image, or chmod -R u+w the directory before the
  rmdir.
